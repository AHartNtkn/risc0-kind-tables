# Kinds follow the forwarder

A resource's kind is fixed. It is the hash of the resource's logic ref and label ref, and the resource's commitment covers both. What is not fixed is the point the compliance circuit uses for that kind when it builds the delta — the kind point. The circuit takes it from the table in force when the proof is made, and uses the kind itself when the table has no entry for it. The delta check is per transaction. So assigning a kind a new kind point does not, by itself, make resources of that kind unusable: a transaction that consumes them balances as long as every resource in it uses the table in force. Two things do go wrong, and they are the only rules.

**R1 — One forwarder.** Two kinds may share one kind point only if one forwarder holds the tokens behind both. Otherwise a token deposited under one kind can be withdrawn under another. This is the rule that protects funds, and it is why sharing a kind point is reviewed like a permission to create tokens.

**R2 — Exit.** A kind with unspent resources must always have a way out: the forwarder accepts its logic ref, so its resources unwrap; or its kind point equals that of a kind the forwarder accepts, so its resources convert first. This is the rule that keeps resources usable. It breaks when the forwarder has moved to a new logic ref and the entry that let the old resources convert is gone.

So a table is a set of fungibility domains. A fungibility domain is one forwarder holding one token on one chain, and the kinds whose resources those tokens back. Every member is assigned the fungibility domain's kind point: the kind of the active circuit version under the current forwarder's label. That version's entries are therefore assigned their own kind, and every other member is an alias of them. The members are every listed circuit version under the current forwarder's label, and, for a forwarder whose tokens moved to the current one, the logic refs it accepted under its own label. Generic call and padding have no fungibility domain: their resources are ephemeral, so nothing is ever made fungible with them, and their entries are assigned their own kind, which the circuit would use anyway.

Which kind point a fungibility domain uses does not matter for safety: moving a whole fungibility domain to a new one only makes in-flight transactions re-prove. So the kind point follows the active version, the one the backend creates resources of. A release makes the new version active and the previous one deprecated, which moves every ERC20 kind point on every chain to the new version's kind and turns the previous version's rows into aliases. The active version keeps its own kind so that it needs no table to know its kind point; the deprecated versions are what the table exists for. Exactly one version is active, and it is the highest listed: an older version never becomes active again, because a broken release is refused at the adapter and replaced by a higher one, and the backend can go back to creating an older version without any change to the table.

The protocol adapter, not the table, stops a broken circuit. The table can only change what a circuit's resources are fungible with, and anyone can prove with a published circuit on their own machine. A version the adapter refuses stays listed, with rows that nothing can use and that cost nothing.

## Consequences

- `data/circuit-versions.json` is the one authored decision: the ERC20 circuit versions, each with its logic ref and its status. A release appends the new version as active and sets the previous one to deprecated; the generator requires exactly one active version, the highest listed. The generator checks every version whose crate is pinned against the logic ref that crate compiles to, so raising a pin without listing the release fails the build.
- The active version's entries are assigned their own kind, so the circuit computes them without the table; every other member is an alias the table must carry. `anoma-rm-risc0` 2.0.0-rc.5 reads each `kind_point` from the file, so a table loaded through it carries every member of a fungibility domain (ADR-0004).
- The `erc20_entries_share_their_fungibility_domains_kind_point` test checks the embedded tables offline: an ERC20 entry is assigned its fungibility domain's kind point, and every other entry is assigned its own kind.
- The promotion gate reads each chain's ERC20 forwarder and requires that the logic ref it accepts is listed. That is R2, checked on chain.
- A retired forwarder is recorded in the forwarder repository's deployment record, verified there against the chain, and read here. Until the bindings expose that record, the generator writes no member under a retired label.
- Nothing checks that a listed version stays listed. A deleted line is the one edit review must catch, and `CODEOWNERS` routes it to a named person.
